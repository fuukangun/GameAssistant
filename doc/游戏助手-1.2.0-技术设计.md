# 游戏助手 1.2.0 - 技术设计

> **版本**: v1.1  
> **日期**: 2026-07-03  
> **关联需求**: [游戏助手-1.2.0-需求文档.md](./游戏助手-1.2.0-需求文档.md)

> **目标版本**: 1.2.0  
> **主题**: 季节日历与后续规划能力

---

## 一、设计目标

1. 新增日历 Tab，用当前存档日期展示当季 28 天网格、NPC 生日、节日和关键预警。
2. 将生日规划从“当天生日提醒”扩展为“生日所在周提前规划”，并严格受送礼次数、剩余可送礼天数和周边界约束。
3. 补全节日静态数据，支持多日节日、提前提醒、当天提醒和去重规则。
4. 冬日星盛宴作为独立特殊事件处理，不与普通 NPC 周送礼额度混算。
5. 日历事件聚合和预警生成必须是可单元测试的纯函数，不依赖 DOM 或 React 渲染。
6. 日历 UI 必须独立组件化，`App.tsx` 只做 Tab 注册和面板挂载，避免继续扩大主组件。
7. CI 测试只依赖仓库内静态数据、脱敏 fixture 或手写最小快照，不依赖本机真实存档路径。

## 三、总体方案

### 3.1 方案选择

日历能力有三种可选实现方式：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 直接在 `generatePlan.ts` 生成日历提醒 | 可复用现有提醒结构 | 会继续扩大 `generatePlan.ts`，且日历事件不是“今日行动” | 不采用 |
| 直接在 React 组件中聚合日历数据 | UI 开发快 | 规则难单测，生日和节日边界容易回归 | 不采用 |
| 新增纯函数 `calendarPanelModel`，UI 只渲染模型 | 规则可测试，边界清晰，App 接入轻 | 需要新增模型层 | 采用 |

### 3.2 新数据流

```text
StardewSaveSnapshot + PlanDate + AppLanguage
  -> createCalendarPanelModel()
      -> buildSeasonCalendarDays()
      -> buildCalendarEvents()
      -> buildBirthdayWarnings()
      -> buildFestivalWarnings()
      -> mergeAndDedupeWarnings()
  -> CalendarPanel
      -> CalendarGrid
      -> CalendarDayDetails
      -> CalendarWarningList
```

设计原则：

- `calendarPanelModel.ts` 是规则中心，所有日期、预警和去重逻辑都在这里完成。
- `CalendarPanel.tsx` 只做状态和渲染：选中日期、点击事件、键盘访问、详情展示。
- `generatePlan.ts` 保留当天生日和当天节日提醒，不承载季节日历和提前规划。
- 日历 Tab 的提醒列表可以显示动态预警，但不把这些预警混入 `plan.reminders`，避免重复和优先级污染。

## 四、数据模型设计

### 4.1 节日静态数据

扩展 `src/stardew/data/calendar.ts`：

```ts
export interface Festival {
  id: string;
  name: string;
  nameEn: string;
  season: Season;
  day: number;
  endDay?: number;
  timeHint: string;
  timeHintEn: string;
  planningTips: string[];
  planningTipsEn: string[];
  relatedData?: FestivalRelatedData;

export interface FestivalRelatedData {
  shopItems?: Array<number | string>;

  requiredHeartNpc?: string;
  requiredHearts?: number;
  itemCategories?: string[];
```

数据校验规则：

- `day` 必须在 1-28。
- `endDay` 可选；存在时必须满足 `day <= endDay <= 28`。
- `name`、`nameEn`、`timeHint`、`timeHintEn`、`planningTips`、`planningTipsEn` 必填。
- 夜市使用单条数据：`day: 15`、`endDay: 17`。
- 多日节日在展开到日历格子时覆盖 `day...endDay` 每一天。

## 五、日历规则设计

### 5.1 周模型

固定规则：

- 每季 28 天。
- Day 1、8、15、22 是周日。
- Week 1: Day 1-7。
- Week 2: Day 8-14。
- Week 3: Day 15-21。
- Week 4: Day 22-28。

实现：

```ts
export function getWeekNumber(day: number): 1 | 2 | 3 | 4 {
  return Math.floor((day - 1) / 7) + 1 as 1 | 2 | 3 | 4;
}

export function getWeekStartDay(day: number): number {
  return Math.floor((day - 1) / 7) * 7 + 1;
}

export function getWeekEndDay(day: number): number {
  return getWeekStartDay(day) + 6;
}
```

### 5.2 事件生成

生日事件：

- 从 `BIRTHDAYS` 过滤当前 `planDate.season`。
- 每个生日生成一个 `CalendarEvent`。
- 标题使用 `formatNpcName(npc, language)`。
- 事件 ID 使用 `birthday:${season}:${day}:${npc}`。

节日事件：

- 从 `FESTIVALS` 过滤当前 `planDate.season`。
- 单日节日挂载到 `day`。
- 多日节日通过 `day...endDay` 展开到每个日历格子，但共享同一个 `festivalId`。
- 事件 ID 使用 `festival:${season}:${day}:${id}`。

特殊事件：

- 冬日星盛宴仍是 `festival` 事件，同时额外生成 `winter_star` 类型动态预警。
- 不单独解析神秘朋友 NPC；本期只展示通用准备建议。

### 5.3 生日预警

输入：

- 当前日期 `currentDay`。
- 当前季节生日 `birthdayDay`。
- NPC 关系数据 `giftsThisWeek`、`giftedToday`。
- 周起止日期。

核心计算：

```ts
const daysBeforeBirthday = birthdayDay - currentDay;
const weekEndDay = getWeekEndDay(birthdayDay);
const daysAfterBirthdayInWeek = weekEndDay - birthdayDay;
const giftsThisWeek = relationship?.giftsThisWeek ?? 0;
const giftedToday = relationship?.giftedToday;
const todayGiftState = giftedToday === undefined ? 'unknown' : giftedToday ? 'gifted' : 'not_gifted';
const regularGiftSlotsLeft = Math.max(0, 2 - giftsThisWeek);
const todayCountsAsOpportunity = todayGiftState === 'not_gifted';
const preBirthdayGiftOpportunities = todayCountsAsOpportunity
  ? Math.min(daysBeforeBirthday, regularGiftSlotsLeft)
  : Math.min(Math.max(0, daysBeforeBirthday - 1), regularGiftSlotsLeft);
```

说明：

- `daysBeforeBirthday` 只在生日前使用；当天生日时为 0。
- 如果当天已经给该 NPC 送礼，当前日不再算作可补常规礼物日。
- 如果 `giftedToday === undefined`，当前日也不算作确定可补常规礼物日；动态文案应提示玩家先确认今天是否已经送礼。
- 文案不得承诺超过 `preBirthdayGiftOpportunities` 的常规礼物次数。

规则表：

| 条件 | 输出 |
|---|---|
| `birthdayDay < currentDay` | 不生成生日预警 |
| 不在生日所在周 | 不生成生日提前预警 |
| 生日是周日且当天生日 | 生成当天生日提醒，不提示突破第 3 次 |
| 生日前、`giftedToday === undefined` | 提示先确认今日是否已送礼，不把今天计为确定机会；该规则优先于普通机会数文案 |
| 生日前、0 次、`preBirthdayGiftOpportunities >= 2` | 提示生日前可先送满 2 次 |
| 生日前、0 次、`preBirthdayGiftOpportunities === 1` | 提示最多先补 1 次 |
| 生日前、0 次、`preBirthdayGiftOpportunities === 0` | 提示准备生日礼物，不提示补常规礼物 |
| 生日前、1 次、`preBirthdayGiftOpportunities >= 1` | 提示生日前再补 1 次 |
| 生日前、1 次、`preBirthdayGiftOpportunities === 0` | 提示已无可补常规礼物时间 |
| 生日前、2 次 | 提示生日当天可突破上限 |
| 当天生日、0 次、`daysAfterBirthdayInWeek > 0` | 提示生日礼物，说明后续仍有常规送礼机会 |
| 当天生日、0 次、`daysAfterBirthdayInWeek === 0` | 提示生日礼物，不承诺后续常规送礼 |
| 当天生日、1 次 | 提示生日礼物 |
| 当天生日、2 次 | 提示已满但生日可突破上限 |

同周多生日：

- 在同一周内生日数量大于 1 时生成 `multi_birthday_week`。
- 汇总只列 NPC 和 Day，不合并不同 NPC 的 `giftsThisWeek`。
- 汇总优先级为 `info`；如果当前周内 3 天内有多个生日，可提升为 `recommended`。

### 5.4 节日提醒

提醒窗口：

- 7 天前：`info`。
- 3 天前：`recommended`。
- 1 天前：`recommended`。
- 当天：`must_do`。

去重规则：

- 同一节日在同一天最多生成 1 条预警。
- 如果多个窗口理论上同时命中，取优先级最高、距离最近的一条。
- 已过节日不生成提醒。
- 节日当天如果现有 `generatePlan.ts` 已输出同义提醒，日历 Tab 仍可显示事件详情，但日历预警列表不重复显示同义内容。

多日节日：

- 夜市 `day: 15, endDay: 17`。
- Day 14 生成一次“明天开始夜市”最终提醒。
- Day 15-17 每天显示当天行动提醒。
- Day 16/17 不再输出“明天开始夜市”。
- Day 18 之后不再提醒。

### 5.5 节日智能建议

P0 只保证通用 `planningTips`。P1 可扩展存档驱动建议：

| 节日 | 数据源 | 计算方式 |
|---|---|---|
| 复活节 | `snapshot.wallet.money` | 与 `relatedData.budgetSuggestion` 比较 |
| 花舞节 | `snapshot.relationships` | 查目标 NPC 心数是否达到 `requiredHearts` |
| 夏威夷宴会 | `snapshot.inventory` | 查高品质可食材候选 |
| 星露谷展览会 | `snapshot.inventory` | 粗略统计展品类别覆盖数 |
| 冰钓节 | `snapshot.player.equipment.fishingRodName` | 未拥有鱼竿时提示提前获取 |
| 冬日星盛宴 | `snapshot.inventory` + 礼物偏好 | 本期通用提示，后续可按神秘朋友解析增强 |

所有智能建议都必须遵循保守原则：数据不足时退化为通用建议，不输出强结论。

## 八、与现有提醒系统的关系

### 8.1 保留现有当天提醒

`generatePlan.ts` 当前已有：

- `buildFestivalReminders()`：当天节日提醒。
- `buildBirthdayReminders()`：当天生日提醒。

1.2.0 不要求立即删除或重写这两个函数。日历 Tab 独立显示季节视图和提前规划。

### 8.2 避免重复

日历 Tab 内部规则：

- 当天生日可以在日历详情中展示。
- 如果 `plan.reminders` 已有当天生日强提醒，日历预警列表不重复生成同义“今天生日必须做”条目，或以较轻量详情形式展示。
- 当天节日同理：日历格子和详情显示事件，预警列表避免重复同义提醒。

技术实现：

- `CalendarWarning` 增加稳定 `id`。
- 对于当天生日/节日，可通过 `suppressDuplicateTodayWarnings` 选项控制是否在预警列表显示。
- P0 推荐默认压制当天同义预警，只在日期详情显示当天事件。

- 国际化：
  - 中文模式无裸英文节日名。
  - 英文模式无中文节日名和中文提示。

### 9.2 静态数据测试

## 十、P1 增强技术方案

P1 目标是围绕 P0 日历能力做体验和可维护性增强，不改变 P0 发版闭环。所有 P1 改动应保持可独立验收，任一项延期时不得影响日历 Tab、生日预警和节日提醒的 P0 可用性。

### 10.1 CalendarPanel 和模型边界细化

当 P0 `CalendarPanel.tsx` 或 `calendarPanelModel.ts` 明显膨胀后，优先按以下边界拆分：

```text
src/app/calendar/
  CalendarPanel.tsx
  CalendarGrid.tsx
  CalendarDayCell.tsx
  CalendarDayDetails.tsx
  CalendarWarningList.tsx
  CalendarEventBadge.tsx
  calendarPanelModel.ts
  calendarDateRules.ts
  calendarEvents.ts
  calendarWarnings.ts
  calendarFestivalSuggestions.ts
  calendarMessages.ts
```

拆分原则：

- `calendarDateRules.ts` 只承载周模型、日期范围、多日节日展开等纯日期规则。
- `calendarEvents.ts` 只负责从 `BIRTHDAYS`、`FESTIVALS` 构造 `CalendarEvent`。
- `calendarWarnings.ts` 负责生日预警、节日提前提醒、冬日星盛宴特殊提醒和去重。
- `calendarFestivalSuggestions.ts` 负责 P1 存档驱动节日建议，不影响 P0 通用 `planningTips`。
- `calendarMessages.ts` 统一动态文案参数化，组件不拼接完整业务句子。
- React 子组件只消费 ViewModel，不读取 store，不重新计算业务规则。

验收标准：

- 日期、事件、预警、文案、智能建议可以分别单元测试。
- `CalendarPanel.tsx` 只保留选中日期、事件点击、预警点击和布局组合逻辑。
- 拆分后 P0 `calendarPanelModel.test.ts` 仍全部通过，测试断言不依赖组件内部结构。

### 10.2 App.tsx 页面结构拆分

P1 可从 `App.tsx` 抽取稳定 UI 区块，降低日历接入后的主组件复杂度：

```text
src/app/components/
  Sidebar.tsx
  PlanHeader.tsx
  SummaryCards.tsx
  RouteProgress.tsx
  RecommendationTabsPanel.tsx
src/app/components/tabs/
  ActionsTab.tsx
  CalendarTab.tsx
  FriendshipTab.tsx
  SkillsTab.tsx
  ExplorationTab.tsx
  ItemsTab.tsx
```

拆分顺序：

1. 先抽取纯展示组件：`Sidebar`、`PlanHeader`、`SummaryCards`、`RouteProgress`。
2. 再抽取 Tab 面板组件，优先把 `CalendarTab` 作为新增独立面板落地。
3. 最后收口 `RecommendationTabsPanel` 的 Tab 分支渲染，`App.tsx` 保留数据准备和顶层状态。

约束：

- 第一阶段使用 props-only 组件，不在抽出的组件内直接访问 store。
- 不改变现有 Tab 排序、筛选、语言切换和错误态行为。
- 每次抽取只移动一个稳定 UI 区块，避免与日历业务规则改动混在一起。

验收标准：

- `App.tsx` 中不再内联日历网格、预警列表和事件详情。
- 抽取前后的用户可见行为一致。
- 组件 props 命名与现有领域对象一致，避免为拆分引入新的状态模型。

### 10.3 generatePlan.ts 规则拆分

P1 可把生日、节日、友谊相关的提醒构建逻辑从 `generatePlan.ts` 中抽出，但 `generatePlan()` 仍作为推荐计划编排入口。

建议目录：

```text
src/stardew/planner/rules/
  birthdayReminders.ts
  festivalReminders.ts
  friendshipReminders.ts
  giftCandidates.ts
```

拆分原则：

- `birthdayReminders.ts` 只保留当天生日提醒和与推荐计划相关的生日行动，不承载日历周视图。
- `festivalReminders.ts` 只保留当天节日提醒，与日历提前提醒通过共享静态数据保持一致。
- `friendshipReminders.ts` 处理友谊维系、低心数、可送礼目标等通用提醒。
- `giftCandidates.ts` 处理可送礼候选构造，供当天计划和日历详情复用。
- 日历 Tab 的提前规划仍由 `calendarWarnings.ts` 生成，避免把季节视图重新塞回推荐计划。

验收标准：

- `generatePlan()` 变成顺序清晰的规则编排，不再直接承载生日、节日、友谊分支细节。
- 现有计划推荐输出保持兼容。
- 生日和节日静态数据只有一套来源，不出现日历和当天提醒日期不一致。

### 10.4 稳定测试夹具

P1 应为日历功能建立仓库内稳定 fixture，避免测试依赖本机真实存档或完整大存档。

建议结构：

```text
src/stardew/fixtures/calendarSnapshots.ts
src/app/calendar/calendarPanelModel.fixtures.ts
```

夹具覆盖：

- 生日前 2 天、1 天、当天、生日后。
- 周日生日、周六生日、同周多生日。
- `giftedToday` 为 `true`、`false`、`undefined`。
- 夜市 Day 14-18。
- 冬日星盛宴 Day 25。
- 钱包、好感、库存、鱼竿状态满足或不满足智能节日建议。

要求：

- fixture 只包含测试需要的最小 `StardewSaveSnapshot` 字段。
- fixture builder 支持覆盖 `planDate`、`relationships`、`inventory`、`wallet`、`equipment`。
- 测试名称描述玩家场景，而不是只描述实现分支。

### 10.5 节日智能建议

P1 智能建议作为 `calendarFestivalSuggestions.ts` 的独立能力接入。输入为节日静态数据、当前快照和语言，输出为附加 `CalendarWarning` 或事件详情中的动态建议。

建议接口：

```ts
export interface FestivalSuggestionInput {
  festival: Festival;
  snapshot: StardewSaveSnapshot;
  language: AppLanguage;
}

export interface FestivalSuggestion {
  id: string;
  priority: CalendarPriority;
  message: string;
  evidence: string[];
}
```

规则：

- 复活节：当 `wallet.money < budgetSuggestion` 时提示金币不足；金币足够时只给轻量确认，不制造强提醒。
- 花舞节：当目标 NPC 或候选舞伴好感不足 4 心时提示还差多少；无法判断目标时使用通用建议。
- 夏威夷宴会：只在库存存在明确高品质食材时提示“已有候选”；无法判定品质时不输出强结论。
- 星露谷展览会：按物品类别做粗略覆盖统计，低覆盖时提示补类别，不承诺最终评分。
- 冰钓节：未解析到鱼竿或无鱼竿时提示提前准备；已拥有时不重复打扰。
- 冬日星盛宴：本期无法确定神秘朋友时不猜 NPC，只基于通用礼物偏好和库存给准备建议。

验收标准：

- 数据明确时输出可解释建议，`evidence` 能说明依据。
- 数据不足时回退到 `planningTips`，不输出误导性强结论。
- P1 智能建议失败不影响 P0 节日展示和提醒生成。

## 十一、P2 预研技术方案

P2 属于后续优化池。本设计只定义技术方向、输入输出和预研验收，不要求在 1.2.0 P0 发版前实现。

### 11.1 历史记录和趋势分析

目标：

- 在用户导入或刷新存档后保存轻量快照，用于展示金币增长、技能变化、友谊推进和关键进度趋势。
- 只读存档，不写回游戏文件。

建议模型：

```ts
export interface DailySnapshotRecord {
  id: string;
  saveId: string;
  recordedAt: string;
  gameDate: PlanDate;
  money: number;
  skillLevels: Record<string, number>;
  friendshipSummary: {
    npcCount: number;
    maxHeartsCount: number;
    lowHeartCount: number;
  };
  communityCenterSummary?: {
    completedBundles: number;
    totalBundles: number;
  };
}
```

技术方向：

- 优先封装 `HistoryRepository` 接口，不让 UI 直接绑定具体存储实现。
- 桌面端可评估 Tauri 本地存储能力；浏览器降级可使用 localStorage 或 IndexedDB 包装。
- 快照写入触发点优先选择“成功解析存档并生成计划后”，避免保存半解析状态。
- 同一 `saveId + gameDate` 可覆盖或合并，避免同一天重复刷新产生大量记录。

预研验收：

- 明确存储方案、数据迁移策略、容量上限和清理策略。
- 给出趋势图最小数据集，不保存完整存档内容。
- 删除本地历史记录不影响存档解析和推荐生成。

### 11.2 社区中心路线规划

目标：

- 从“今天能交什么”扩展到“还缺什么、在哪里获取、当前季节是否能推进、优先做什么”。

建议数据流：

```text
StardewSaveSnapshot.communityCenter
  + inventory
  + PlanDate
  + bundle static data
  + item source catalog
  -> buildCommunityCenterRoutePlan()
  -> missing items / available turn-ins / seasonal opportunities / priority actions
```

核心模型：

```ts
export interface CommunityCenterRoutePlan {
  completedBundles: CommunityBundleProgress[];
  availableTurnIns: CommunityTurnInCandidate[];
  missingItems: CommunityMissingItem[];
  priorityActions: CommunityRouteAction[];
}
```

技术方向：

- 先补齐 bundle 静态数据和物品来源目录，再做路线排序。
- 规划输出必须区分“已在库存中”“当前季节可获得”“未来季节可获得”“来源未知”。
- 初版使用规则排序，不引入复杂求解器；优先级依据季节窗口、库存可交付、收益和阻塞程度。
- 与日历 Tab 可共享节日和季节信息，但不把社区中心路线混入 P0 日历模型。

预研验收：

- 能基于脱敏 fixture 输出缺失物品、可交付物品和当前季节建议。
- 对来源未知或解析不完整的物品保持保守提示。
- 不要求预测精确完成日期。

### 11.3 Web Worker 性能优化

目标：

- 评估存档解析、推荐生成、日历模型生成是否会阻塞 UI，并在必要时迁移 CPU 密集任务到 Worker。

候选边界：

```text
main thread
  -> ParseAndPlanWorker request
worker
  -> importSaveFile()
  -> parseSave()
  -> generatePlan()
  -> createCalendarPanelModel()
main thread
  -> stale result guard
  -> store update
```

消息协议：

```ts
export interface WorkerRequest {
  requestId: string;
  type: 'parse_save' | 'generate_plan' | 'build_calendar';
  payload: unknown;
}

export interface WorkerResponse {
  requestId: string;
  ok: boolean;
  payload?: unknown;
  error?: string;
}
```

技术方向：

- 先增加耗时测量，确认解析或生成阶段的阻塞阈值。
- 主线程保留 `requestId`，只接受最后一次请求结果，丢弃过期响应。
- Worker 错误回传结构化 message，不把异常对象直接暴露给 UI。
- Worker 化不得改变现有模型纯函数输入输出。

预研验收：

- 明确是否需要 Worker、触发阈值和迁移范围。
- 给出最小 Worker 原型或性能测量数据。
- Worker 不可用时仍可回退主线程同步执行。

### 11.4 测试框架迁移评估

目标：

- 评估是否从当前测试方式统一迁移到 Vitest，提升前端组件、纯函数和 fixture 测试的一致性。

评估步骤：

1. 盘点现有测试文件、运行命令、断言风格和覆盖模块。
2. 选择 `calendarPanelModel.test.ts` 或 `recommendationTabs.test.ts` 做最小迁移样例。
3. 比较运行速度、错误输出、TypeScript 支持、React 测试支持和 CI 接入成本。
4. 决定全量迁移、局部保留或暂不迁移。

约束：

- 迁移期间不能出现同一测试被两个 runner 重复执行。
- 不因为迁移测试框架改变业务断言。
- 迁移计划应按模块分批，不把 P0 日历功能阻塞在测试框架切换上。

预研验收：

- 有清晰的迁移收益、成本和风险结论。
- 有一个可运行的样例测试或明确的暂缓理由。

### 11.5 CSS 模块化

目标：

- 降低 `global.css` 继续膨胀和选择器互相影响的风险。

技术方向：

- 新增日历组件优先使用局部样式文件或命名清晰的日历样式块。
- 若引入 CSS Modules，从 `CalendarPanel` 或抽取后的 Tab 组件开始试点。
- 全局主题变量、字体、基础布局仍保留在全局样式中。
- 不在 1.2.0 中做全局样式大迁移。

预研验收：

- 明确 CSS Modules 与当前构建配置的兼容性。
- 完成一个低风险组件的样式隔离样例。
- 样式迁移后中英文、桌面端和移动端布局无回归。

## 十三、风险与降级策略

| 风险 | 影响 | 降级策略 |
|---|---|---|
| 生日送礼边界复杂 | 文案误导玩家 | 所有边界放入 `calendarPanelModel.test.ts`，文案只由模型分支生成 |
| 节日英文数据不完整 | 英文 UI 混入中文 | 静态数据测试强制英文字段完整 |
| 日历 UI 事件过多撑破格子 | 移动端不可用 | 格子内只显示最多 2 条摘要，其余进入详情 |
| `App.tsx` 继续膨胀 | 后续维护困难 | 日历 UI 独立文件，App 只挂载组件 |
| 与现有当天提醒重复 | 用户看到两条同义提醒 | 日历预警列表压制当天同义提醒，详情保留事件 |
| 智能建议数据不足 | 输出过强结论 | P1 建议只在数据明确时输出，否则回退通用 `planningTips` |
| P1 拆分引入行为回归 | 已有 Tab、当天提醒或布局出现变化 | 每次只抽取一个边界，抽取前后保持同一组模型和手工验收 |
| 日历 fixture 过度贴合实现 | 测试只验证内部结构，不验证玩家场景 | fixture 以生日周、节日窗口、库存状态等场景命名和组织 |
| 历史记录保存过多数据 | 本地存储膨胀或包含不必要存档细节 | 只保存趋势所需摘要字段，设置清理策略 |
| 社区中心路线过度承诺 | 玩家误以为系统能预测精确完成日 | P2 初版只输出缺失项、来源和优先级，不承诺精确日期 |
| Worker 化增加状态复杂度 | 过期结果覆盖新结果或错误难排查 | 使用 `requestId` 丢弃过期响应，保留主线程回退路径 |
| 测试框架迁移干扰发版 | P0 功能被工具切换阻塞 | Vitest 只做 P2 评估，P0/P1 不依赖迁移完成 |
| CSS 模块化范围失控 | 样式大迁移带来视觉回归 | 只从新增或已抽取组件试点，不重写全局主题和基础布局 |
