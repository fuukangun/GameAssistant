### 1.2 数据流

```
Tauri后端扫描/解析存档
  │
  ▼
结构化 StardewSaveSnapshot
  │
  ▼
前端选择存档 + 用户选择天气 + 手动校正
  │
  ▼
PlannerInput
  │
  ▼
规则引擎生成 CandidateAction[]
  │
  ▼
可行性过滤 + 优先级分层 + 分数辅助排序
  │
  ▼
PlanRecommendation
```

### 1.2.1 状态管理职责

| Store | 职责 |
|-------|------|
| `saveStore` | 存档列表、选中存档、扫描状态、解析结果缓存 |
| `plannerStore` | 计划输入（天气、目标、手动校正）、生成结果、加载状态 |
| `settingsStore` | 用户配置、存档备注、自定义目录 |

### 1.2.2 前端路由

| 路径 | 页面 | 说明 |
|------|------|------|
| `/` | 存档列表 | 启动默认页 |
| `/save/:id` | 存档详情 | 展示解析结果和关键信息 |
| `/plan/:id` | 每日计划 | 核心功能页 |
| `/settings` | 设置 | 手动目录、默认目标等 |

### 1.3 为什么解析放在Tauri后端

- 本地文件权限、路径处理、编码处理更适合后端统一封装。
- 前端不直接接触任意文件路径，降低安全面。
- 后续可以用Rust测试夹具验证真实存档字段。
- 前端只消费稳定的结构化模型。

### 1.4 Tauri权限边界

`tauri.conf.json` 需要显式声明文件读取和目录选择能力，前端只通过命令层触发：

- `fs:allow-read`
- `fs:allow-exists`
- `dialog:allow-open`

原则：

- 默认只给读取权限。
- 不授予写入游戏存档目录的权限。
- 用户手动选择目录后，权限仍只限于读取该目录。

## 二、技术选型

### 2.1 稳定优先结论

| 层级 | 选型 | 原因 |
|------|------|------|
| 桌面框架 | Tauri 2稳定版 | 已稳定发布，权限/能力模型更适合本地文件访问 |
| 前端框架 | React稳定版 | 生态成熟，组件和状态管理方案稳定 |
| 语言 | TypeScript + Rust | 前端类型安全，后端适合文件与解析 |
| 构建 | Vite稳定版 | 与React/Tauri组合成熟 |
| 状态管理 | Zustand | 简单、低样板，适合桌面工具 |
| UI | shadcn/ui + Tailwind CSS | 组件质量稳定，可控性高 |
| 本地配置 | Tauri Store或应用数据目录JSON | 简单可迁移，MVP无需数据库 |
| XML解析 | Rust XML库 | 后端解析并统一错误处理 |

版本策略：

- 脚手架阶段锁定具体minor/patch版本。
- 不使用实验性API。
- 依赖升级只在单独任务中进行。
- 优先选择文档稳定、社区问题可检索的版本。

### 2.2 暂不采用

- Electron：体积和资源占用更高，MVP没有必须使用Node集成的理由。
- 真正插件系统：抽象成本过早。
- SQLite：MVP只有设置、备注和少量缓存，JSON足够。
- SMAPI实时Mod：本期不做。

## 三、存档解析设计

### 3.1 存档位置

| 平台 | 默认路径 |
|------|----------|
| Windows | `%AppData%/StardewValley/Saves/` |
| macOS | `~/.config/StardewValley/Saves/` |
| Linux | `~/.config/StardewValley/Saves/` |

每个存档通常是一个文件夹，包含：

- 主存档XML文件：通常与文件夹同名。
- `SaveGameInfo`：存档列表摘要文件。
- `_old`备份文件。

扫描策略：

1. 扫描默认路径。
2. 找不到则允许用户手动选择目录。
3. 目录下按“包含主存档文件或SaveGameInfo”的规则识别。
4. 解析失败的存档仍显示在列表中，但状态为“解析失败”。

### 3.1.1 Tauri命令签名

```rust
#[tauri::command]
async fn scan_saves(custom_path: Option<String>) -> Result<Vec<SaveEntry>, AppError>

#[tauri::command]
async fn parse_save(save_path: String) -> Result<StardewSaveSnapshot, AppError>

#[tauri::command]
async fn load_config() -> Result<LocalAppConfig, AppError>

#[tauri::command]
async fn save_config(config: LocalAppConfig) -> Result<(), AppError>
```

### 3.3 关键字段

MVP必须解析或降级处理以下字段：

| 字段 | 用途 | 失败影响 |
|------|------|----------|
| 玩家名、农场名 | 存档列表 | 可用文件夹名降级 |
| 年、季节、日 | 计划日期 | 解析失败则不能生成计划 |
| 金钱 | 赚钱建议、Joja建议 | 相关建议降级 |
| 技能等级 | 钓鱼/采矿估算 | 收益估算降级 |
| 背包物品 | 生日礼物、社区中心 | 礼物建议降级 |
| 农场作物 | 收获/季末风险 | 农业建议降级 |
| 社区中心/Joja状态 | 路线建议 | 路线建议隐藏或低置信 |
| 已达矿洞深度 | 后续矿洞目标 | MVP只展示，不做核心排序 |

### 3.4 解析与路线判断说明

- 存档路径优先通过 `dirs` 类库解析，不硬编码平台路径逻辑。
- `whichFarm` 的数值与字符串值都应映射到统一农场类型。
- 路线判断优先级：Joja明确标记 > 社区中心完成状态 > 关键邮件/事件推断 > unknown。
- `uniqueIDForThisGame` 作为备注主键；若缺失，则使用文件路径。
- XML 解析以 UTF-8 为默认编码，并遵循文件头声明；若解码失败，尝试 UTF-8 fallback，仍失败则报错。

### 3.5 真实存档验证矩阵

在开发前建立 fixtures，不依赖猜测字段路径。

| Fixture | 目的 |
|---------|------|
| 新档春季早期 | 验证基础字段 |
| 第一年夏季中期 | 验证作物、生日、天气输入 |
| 季节第28天 | 验证跨季计划和作物风险 |
| 社区中心部分完成 | 验证bundle解析 |
| Joja路线 | 验证不输出社区中心建议 |
| 矿洞已推进 | 验证进度字段 |
| 1.6存档 | 验证新字段和农场类型 |
| 含Mod字段存档 | 验证忽略未知字段 |
| 多人存档样本 | MVP不专项支持，但必须不崩溃 |

每个fixture需要记录：

- 游戏版本。
- 存档来源。
- 预期解析字段。
- 已知不可解析字段。
- 对应测试用例。

### 3.6 解析错误模型

```typescript
export interface ParseWarning {
  code:
    | 'missing_field'
    | 'unknown_game_version'
    | 'unsupported_multiplayer'
    | 'modded_field_ignored'
    | 'bundle_parse_failed'
    | 'crop_parse_failed';
  severity: 'info' | 'warning' | 'error';
  message: string;
  fieldPath?: string;
}
```

规则：

- `failed`：缺少年/月/季/日等生成计划所需字段。
- `partial`：基础字段可用，但部分建议所需字段缺失。
- `ok`：MVP关键字段都正常。

## 四、计划输入模型

```typescript
export interface PlannerInput {
  snapshot: StardewSaveSnapshot;
  planDate: PlanDate;
  selectedWeather: Weather;
  goal: PlannerGoal;
  manualCorrections: ManualCorrections;
}

export type PlannerGoal = 'free' | 'money';

export type Weather =
  | 'sunny'
  | 'rainy'
  | 'stormy'
  | 'snowy'
  | 'windy';

export interface ManualCorrections {
  wateredToday: boolean;
  harvestedToday: boolean;
  giftedToday: boolean;
}
```

天气解析规则：

1. MVP不将存档内 `weatherForTomorrow` 作为今日天气默认值。
2. 今日天气由用户手动选择；默认值仅作为UI兜底，不声明来自存档。
3. 若后续能可靠解析当天实际天气，可再作为默认值接入。

原因：

- 星露谷主存档日期与读档进入游戏后的当天一致，因此计划日就是存档日期。
- `weatherForTomorrow` 对应存档日的明日天气，不能作为今日天气。
- 用户覆盖能力保留，避免存档与实际游戏状态不一致时误导建议。

## 五、建议引擎设计

### 5.1 总体策略

建议引擎采用“规则优先 + 分数辅助”。

不直接向用户展示总分，避免让用户误以为软件进行了精确优化。排序内部可以使用分数，但输出必须解释成自然语言：为什么推荐、依据是什么、哪里不确定。

流程：

```
生成基础提醒
  │
  ├─ 日历规则：生日、节日、季末、季初
  ├─ 路线规则：社区中心/Joja
  └─ 天气规则：雨天、雷暴、雪天

生成候选行动
  │
  ├─ 收获作物
  ├─ 种植/购买种子
  ├─ 钓鱼赚钱
  ├─ 觅食
  ├─ 送礼
  └─ 社区中心/Joja进度

可行性过滤
  │
  ├─ 金钱是否足够
  ├─ 季节/天气是否满足
  ├─ 是否已手动标记完成
  ├─ 解锁条件是否满足
  └─ 数据是否足够支持建议

优先级分层
  │
  ├─ P0 必做提醒
  ├─ P1 时限机会
  ├─ P2 高收益行动
  ├─ P3 进度推进
  └─ P4 可选维护

分数辅助排序
  │
  ├─ urgencyScore
  ├─ profitScore
  ├─ progressScore
  ├─ feasibilityScore
  ├─ riskPenalty
  └─ confidenceWeight

输出建议
```

### 5.2 推荐项模型

### 5.3 优先级层级

| tier | 用户展示 | 定义 | 示例 |
|------|----------|------|------|
| 0 | 必做 | 今天错过会造成明显损失 | 季末收获、生日、节日 |
| 1 | 推荐 | 今天条件满足且机会有限 | 限定鱼、雷暴电池 |
| 2 | 推荐 | 可估算收益高 | 成熟作物、钓鱼 |
| 3 | 可选 | 推进长期目标 | 社区中心缺项、Joja资金 |
| 4 | 可选 | 维护性行动 | 清理农场、整理背包 |

tier先于total排序。也就是说，P0提醒不会因为金币收益低而被赚钱行动压下去。

### 5.4 内部分数公式

内部排序公式：

```typescript
total =
  urgency * goalWeights.urgency +
  profit * goalWeights.profit +
  progress * goalWeights.progress +
  feasibility * goalWeights.feasibility +
  confidence * goalWeights.confidence -
  riskPenalty;
```

目标权重：

```typescript
export const GOAL_WEIGHTS = {
  free: {
    urgency: 0.35,
    profit: 0.20,
    progress: 0.20,
    feasibility: 0.15,
    confidence: 0.10,
  },
  money: {
    urgency: 0.20,
    profit: 0.45,
    progress: 0.10,
    feasibility: 0.15,
    confidence: 0.10,
  },
} as const;
```

分数范围统一为0-100。

### 5.5 urgencyScore

时限越强，分数越高。

| 条件 | 分数 |
|------|------|
| 今天不做就错过或损失 | 100 |
| 1-2天内窗口关闭 | 80 |
| 本季内需要处理 | 50 |
| 无明确时限 | 20 |
| 纯维护事项 | 10 |

示例：

- 季节第28天收获不跨季作物：100。
- NPC生日：100。
- 节日当天：100。
- 夏季晴天限定鱼：80。
- 社区中心长期缺项：40-60。

### 5.6 profitScore

收益分数只对可估算金币收益有效。

基础公式：

```typescript
profitScore = clamp(normalizedGoldValue * certaintyModifier, 0, 100)
```

MVP归一化建议：

| 预计金币收益 | profitScore |
|--------------|-------------|
| 0或不可估算 | 0 |
| 1-300 | 20 |
| 301-1000 | 40 |
| 1001-3000 | 65 |
| 3001-8000 | 85 |
| 8000以上 | 100 |

收益口径：

- 成熟作物：固定收益或较窄估算，certaintyModifier = 1.0。
- 钓鱼：区间估算，certaintyModifier = 0.6-0.8。
- 觅食：若未解析地图物品，certaintyModifier = 0.4。
- 未来种植：属于 projected，certaintyModifier = 0.7。

### 5.7 progressScore

长期推进分数基于解锁价值和当前距离。

| 条件 | 分数 |
|------|------|
| 今天可直接完成重要解锁 | 100 |
| 今天可完成社区中心/Joja关键步骤 | 80 |
| 离完成只差少量物品或金钱 | 60 |
| 普通长期积累 | 30 |
| 与当前进度关系弱 | 0-10 |

MVP中，progressScore不应压过P0提醒。它主要用于自由模式中区分“顺手推进”和“完全不急”。

### 5.8 feasibilityScore

可行性来自当前状态、解锁、资金、季节、天气、手动校正。

| 条件 | 分数 |
|------|------|
| 当前明确可做 | 100 |
| 大概率可做，但缺少少量数据 | 70 |
| 需要用户确认 | 50 |
| 条件不足但可准备 | 25 |
| 不可做 | 0，通常过滤掉 |

过滤规则优先于评分：

- 钱不够的购买类活动直接过滤或显示为“还差X金”。
- 季节不满足的作物直接过滤。
- 用户标记已收获后，不再推荐收获。
- Joja路线下过滤社区中心收集建议。

### 5.9 confidenceScore

| 置信度 | 分数 | 规则 |
|--------|------|------|
| 高 | 100 | 静态日历、明确存档字段、用户输入 |
| 中 | 65 | 存档字段明确但当天可能已变化 |
| 低 | 35 | 随机性强、依赖玩家操作、字段部分缺失 |

置信度必须体现在输出文案中，而不仅用于排序。

### 5.10 riskPenalty

风险扣分避免推荐“收益高但容易误导”的行动。

| 风险 | 扣分 |
|------|------|
| 字段缺失导致估算不完整 | 10-25 |
| 玩家当天可能已完成 | 10 |
| 依赖随机性或操作水平 | 10-30 |
| 可能与节日/商店时间冲突 | 20-40 |
| 可能导致作物无法成熟 | 50以上 |

### 5.11 建议生成示例

输入：

- 存档日期：夏15。
- 计划日期：夏15。
- 用户选择天气：晴天。
- 背包：紫水晶。
- 作物：12株蓝莓成熟。
- 生日：塞巴斯蒂安。

输出排序：

1. 塞巴斯蒂安生日送紫水晶  
   tier=0，urgency=100，confidence=100。

2. 收获成熟蓝莓  
   tier=2，profit=65，confidence=65，riskPenalty=10。

3. 晴天钓鱼赚钱  
   tier=2，profit=40-65，confidence=35，riskPenalty=20。

前端展示不显示数字，只展示：

- 必做/推荐/可选。
- 高/中/低置信度。
- 预计收益或区间。
- 数据依据和不确定项。

## 七、静态数据

### 7.1 数据文件

| 文件 | 内容 |
|------|------|
| `calendar.json` | 节日、生日、季节日期 |
| `crops.json` | 作物季节、生长天数、复收、售价、跨季 |
| `fish.json` | 鱼类季节、天气、时间、地点、价格 |
| `npcs.json` | NPC生日、喜欢/最爱礼物 |
| `bundles.json` | 社区中心收集包 |
| `prices.json` | 物品基础售价和品质倍率 |
| `joja.json` | Joja项目和价格 |

### 7.2 数据版本

每个静态数据文件包含：

```json
{
  "gameVersion": "1.6.x",
  "dataVersion": "2026-06-18",
  "source": "Stardew Valley game data / wiki cross-check",
  "items": []
}
```

开发时不应把数据散落在规则代码里。规则代码只引用数据ID和标准字段。

### 7.3 启动校验

- 启动时校验静态数据的必填字段是否齐全。
- `gameVersion` 和当前支持的解析版本不匹配时给出告警，但不阻断启动。
- 静态数据文件损坏时，将对应数据源标记为不可用，相关建议降级为低置信度。

## 八、社区中心与Joja路线

### 8.1 路线状态

```typescript
export type RouteState =
  | { kind: 'community_center'; confidence: Confidence }
  | { kind: 'joja'; confidence: Confidence }
  | { kind: 'unknown'; confidence: 'low' };
```

### 8.2 规则

- 社区中心路线：允许生成收集包建议。
- Joja路线：禁止生成社区中心收集建议。
- unknown：不生成强社区中心建议，只展示低置信度提示。

### 8.3 进度展示

社区中心进度不要只用简单百分比代替详细状态。MVP可以展示：

- 已完成房间数量。
- 可识别的剩余关键物品数量。
- 今日可完成的收集项。

Joja展示：

- 已完成项目。
- 未完成项目。
- 距离最低价未完成项目还差多少金。

### 10.2 错误分类

| code | 场景 | recoverable |
|------|------|-------------|

|------|----------|

## 十三、后续扩展预留

### 13.1 SMAPI实时模式

本期不做。若后续加入，应作为独立增强项目：

- 单独SMAPI Mod。
- 本地只监听 `127.0.0.1`。
- 随机token或本地认证。
- 端口冲突处理。
- 游戏未加载存档时返回明确状态。
- 桌面端可降级回离线模式。

### 13.2 多游戏插件

本期不做。等星露谷规则稳定后，再从第二款游戏抽象接口。

当前只保持内部边界清晰：

- 存档解析。
- 静态数据。
- 规则引擎。
- UI展示。

不要为了未知游戏提前设计外部插件协议。

### 13.3 数据更新机制

- 静态数据与代码同仓库存放。
- 每次更新作物、鱼、NPC、节日或Joja数据时，都要同步更新 `gameVersion` 和 `dataVersion`。
- 数据来源需在 PR 或变更说明中注明。
